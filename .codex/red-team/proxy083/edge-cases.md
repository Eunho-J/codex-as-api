## 사례 목록

### 묶음 1: 클라이언트 중립 진입, 세션·계정 격리, 공유 제어의 엔드포인트 간 일관성

프록시가 요청을 처음 수신할 때 가장 먼저 판정해야 하는 질문은 어떤 클라이언트의 요청을 허용하고, 어떤 제어 속성을 검증한 뒤 상위 공급자 요청에 남기거나 제거할 것인가이다. 일반 클라이언트에 특정 에이전트 신원을 강제하던 제약을 풀더라도, 기존 전송 경로와 계정 격리 및 명시적 캐시 키 우선순위는 흔들리지 않아야 한다. 나아가 `Messages`에서 유효하다고 인정한 공통 제어값은 토큰 계산(`count`)과 문맥 압축(`compact`)에서도 같은 기준으로 수용되어야 클라이언트가 단일 대화 흐름을 끊김 없이 이어갈 수 있다.

### EC-001. Claude Code 식별이 없는 일반 Messages 요청 허용과 선택적 세션 캐시 친화성 및 계정 격리

- **설계 근거:** 일반 클라이언트는 일반 Messages 요청을 위해 Claude Code 식별 정보를 요구받지 않아야 하며, 기존 유효 전송 경로와 계정 격리는 유지되어야 한다. 선택적 Claude 세션 식별자는 프라이버시 안전 캐시 친화성을 제공할 수 있으나 명시적 키 우선순위와 계정 격리가 유지되어야 한다(`DO-01`).
- **필수 여부:** `required`
- **선행 조건:** 두 개의 서로 다른 계정 상태(`account_A`, `account_B`)가 격리된 상태로 구성되어 있고, 프록시의 Messages 요청 처리 단위가 표준 HTTP/전송 입력을 받을 준비가 되어 있다.
- **입력과 행동 순서:**
  1. `account_A` 문맥에서 Claude Code 전용 헤더·식별자·시스템 프리픽스 없이 표준 클라이언트 헤더와 유효한 `model`, `max_tokens: 256`, `messages: [{"role": "user", "content": "hello"}]`만 포함한 일반 Messages 요청을 전달한다.
  2. `account_A` 문맥에서 동일한 일반 Messages 요청에 선택적 Claude 세션 식별자(`session_id: "sess-alpha-001"`)만 추가하여 전달하고, 생성된 상위 요청의 캐시 친화성 파생 상태 변수를 기록한다.
  3. `account_A` 문맥에서 동일한 `session_id: "sess-alpha-001"`과 함께 명시적 캐시 키(`prompt_cache_key: "explicit-key-99"`)를 동시에 지정하여 전달한다.
  4. `account_B` 문맥에서 `account_A`와 동일한 `session_id: "sess-alpha-001"`을 가진 요청을 전달하고, `account_A`의 세션·캐시 친화성 상태와 비교한다.
- **기대 결과:**
  1. 1단계 요청은 Claude Code 식별 정보 부재를 이유로 거부되지 않고 정상 수락되어 상위 요청 변환 및 응답 반환이 완료된다.
  2. 2단계 요청은 원문 세션 식별자를 그대로 외부에 노출하지 않는 프라이버시 안전 파생 캐시 친화성 값을 형성한다.
  3. 3단계 요청에서는 선택적 세션 식별자보다 명시적 캐시 키(`"explicit-key-99"`)가 우선하여 최종 캐시 키 상태 변수에 명시적 키가 반영된다.
  4. 4단계 요청에서 `account_B`의 캐시 친화성 및 계정 상태 변수는 `account_A`의 상태와 결합되거나 공유되지 않으며, 계정 간 격리가 유지된다.
- **보존 조건:** 기존에 유효하던 전송 방식(헤더·본문 구조)과 각 계정의 인증·라우팅 격리 상태 변수는 1~4단계 실행 전후에 변조되거나 다른 계정으로 누수되지 않아야 한다.
- **정상 대조와 적용 범위:** Claude Code 식별을 갖춘 요청과 갖추지 않은 표준 클라이언트 요청이 모두 일반 Messages 경로에서 동일하게 통과하는지 대조하며, 세션 식별자 단독 제공·명시적 키 동시 제공·타 계정 동일 세션 식별자 제공의 세 가지 경계를 포괄한다.
- **미정 규칙:** 계정 격리는 인증·캐시 저장소 경계의 의미이며, 서로 다른 계정의 동일 명시적 캐시 키 문자열 자체가 달라야 한다는 뜻은 아니다. 세션 식별자의 구체 HTTP 표현은 기존 프로토콜 계약을 사용하고 `session_id`를 새 본문 필드로 추가하지 않는다.

### EC-002. `max_tokens` 양의 안전 정수 검증·힌트 수용과 `Messages`·`count`·`compact` 간 유효 공통 제어 일치

- **설계 근거:** Messages 요청에는 유효한 양의 안전 정수 `max_tokens`가 필수이며 비공개 Codex 출력 상한 약속이 아닌 힌트로 수용된다. 또한 `Messages`, `count`, `compact`는 유효한 공통 제어에 대해 동일하게 판정해야 한다(`DO-02`).
- **필수 여부:** `required`
- **선행 조건:** 동일한 모델 카탈로그와 요청 검증기가 `Messages`, `count`, `compact` 세 요청 경로에 연결되어 있다.
- **입력과 행동 순서:**
  1. `Messages` 경로에 `max_tokens`가 누락된 요청, `0`, `-10`, `3.5`, `"100"`, `9007199254740992`(`Number.MAX_SAFE_INTEGER + 1`)인 요청을 각각 입력한다.
  2. `Messages` 경로에 유효한 양의 안전 정수 `max_tokens: 64`와 높은 값 `max_tokens: 128000`을 각각 입력하고, 변환된 상위 공급자 요청 변수와 응답 처리를 확인한다.
  3. 유효한 공통 제어 조합(`max_tokens: 2048`, `thinking: {"type": "enabled", "budget_tokens": 1024}`, `metadata: {"user_id": "usr_123"}`, 유효한 `cache_control: {"type": "ephemeral"}`, 유효한 `tools` 배열)을 담은 동일 입력을 `Messages`, `count`, `compact` 세 경로에 각각 전달한다.
- **기대 결과:**
  1. 1단계의 누락·0·음수·소수·문자열·비안전 정수 `max_tokens` 입력은 모두 유효성 검증 오류로 거부된다.
  2. 2단계의 `max_tokens: 64` 및 `128000` 입력은 모두 유효한 힌트로 수락되며, 프록시가 임의의 비공개 Codex 출력 토큰 절단 캡을 강제하거나 상위 응답을 임의로 잘라내지 않는다.
  3. 3단계의 유효 공통 제어 조합은 `Messages`, `count`, `compact` 세 경로 모두에서 모순 없이 동일하게 유효한 입력으로 수락된다.
- **보존 조건:** `max_tokens` 검증 실패 시 상위 공급자 호출이나 세션 상태 변수가 생성되지 않아야 하며, 정상 수락 시 함께 전달된 `messages`, `system`, `tools` 내용이 손실되지 않아야 한다.
- **정상 대조와 적용 범위:** `max_tokens: 1` 및 일반 양의 안전 정수(`1024`)를 정상 대조군으로 삼아 하한(`0`, 음수), 자료형 오류(실수, 문자열), 상한(`MAX_SAFE_INTEGER` 초과), 그리고 세 엔드포인트(`Messages`, `count`, `compact`) 간의 공통 제어 수용 일관성을 검증한다.
- **미정 규칙:** 해당 없음.

### EC-003. 임시(`ephemeral`) 캐시 힌트의 사전 검증·제거와 `metadata.user_id` 검증 후 무시

- **설계 근거:** 임시(`ephemeral`) 캐시 힌트는 검증된 뒤 상위 공급자 전달 전에 폐기되며 네이티브 TTL이나 분기점을 약속하지 않는다(`DO-02`). `metadata.user_id`는 선택적 문자열 또는 `null`로만 검증한 뒤 무시하며 인증·세션·계정 메타데이터로 사용하지 않는다(`DO-06`).
- **필수 여부:** `required`
- **선행 조건:** 요청 변환 단위가 클라이언트 요청을 검증한 뒤 상위 공급자용 요청 객체와 내부 인증·세션·계정 상태 변수를 생성하는 단계에 있다.
- **입력과 행동 순서:**
  1. 시스템 프롬프트 블록, 메시지 콘텐츠 블록, 도구 정의에 각각 유효한 `cache_control: {"type": "ephemeral"}`을 포함하고 `metadata: {"user_id": "user-abc-999"}` 및 `metadata: {"user_id": null}`을 설정한 요청을 `Messages`, `count`, `compact`에 전달한다.
  2. 1단계 요청이 검증을 통과한 직후 상위 공급자로 전달되는 요청 페이로드 변수와 인증·세션·캐시 친화성·계정 식별 상태 변수를 확인한다.
  3. `cache_control: {"type": "persistent"}` 또는 비객체 값(`cache_control: "ephemeral"`)을 포함한 요청과, `metadata: {"user_id": 12345}` 또는 `metadata: {"user_id": {"id": "x"}}`를 포함한 요청을 각각 전달한다.
- **기대 결과:**
  1. 1단계의 유효한 임시 캐시 힌트와 문자열·`null` 형태의 `metadata.user_id`는 세 경로 모두에서 정상 수락된다.
  2. 2단계의 상위 공급자 요청 페이로드 변수에는 `cache_control` 필드나 가짜 네이티브 TTL/분기점 필드가 남아 있지 않으며, 인증·세션·계정·캐시 친화성 상태 변수 어디에도 `"user-abc-999"`가 저장되거나 반영되지 않는다.
  3. 3단계의 잘못된 `cache_control` 형식과 문자열·`null`이 아닌 `metadata.user_id` 입력은 검증 단계에서 명시적 오류로 거부된다.
- **보존 조건:** `cache_control` 힌트가 제거되더라도 해당 시스템 블록, 메시지 텍스트 블록, 도구 정의의 본래 텍스트와 스키마 필드는 상위 요청 페이로드에 그대로 보존되어야 한다.
- **정상 대조와 적용 범위:** `cache_control`과 `metadata`가 전혀 없는 기본 요청을 정상 대조군으로 삼아, 유효한 `ephemeral` 힌트와 `user_id`(`string`/`null`)가 들어왔을 때 상위 요청과 세션 상태가 대조군과 동일하게 깨끗한지, 그리고 잘못된 자료형이 들어왔을 때 즉시 거부되는지 검증한다.
- **미정 규칙:** 해당 없음.

### 묶음 2: 스트리밍 초기·최종 사용량 교체와 프로토콜별 캐시 토큰 산출

요청이 상위 공급자로 전달된 뒤 응답이 돌아오는 단계에서는 스트리밍 이벤트 진행에 따른 사용량(usage) 변수의 수명주기와 Anthropic·OpenAI 두 출력 프로토콜 간의 토큰 계산 관계가 핵심 검증 대상이 된다. 앞 묶음에서 캐시 힌트와 요청 제어를 정규화했다면, 이 묶음에서는 상위 공급자가 보고하는 원시 토큰 수치와 캐시 읽기·쓰기 수치가 스트림 시작과 종료 시점, 그리고 프로토콜별 응답 구조에서 어떻게 변환·보존·거부되는지 확인한다.

### EC-004. 스트리밍 시작 이벤트의 임시 0 사용량 표기와 완료 이벤트의 최종 확정치 대체

- **설계 근거:** 초기 스트림 이벤트는 임시 숫자 `0`의 입력·출력 사용량을 포함하며, 최종 확정 합계가 도착하면 임시값을 대체한다(`DO-03`).
- **필수 여부:** `required`
- **선행 조건:** 스트리밍 응답 변환기가 활성화되어 있고, 상위 스트림이 시작 시점에는 확정 사용량을 주지 않다가 종료 시점에 확정 사용량(`input: 140, output: 35`)을 전달한다.
- **입력과 행동 순서:**
  1. 스트리밍 요청을 시작하고 상위 스트림의 첫 응답 시작 이벤트를 주입하여 프록시가 방출하는 첫 스트림 이벤트(`message_start` 등 초기 사용량 포함 이벤트)의 `usage` 객체 값을 확인한다.
  2. 본문 델타 이벤트들을 순서대로 통과시킨다.
  3. 상위 스트림의 완료 이벤트에 최종 확정 사용량(`input: 140, output: 35`)을 담아 주입하고, 프록시가 방출하는 최종 사용량 이벤트(`message_delta` 및 최종 상태 변수)를 확인한다.
- **기대 결과:**
  1. 초기 스트림 이벤트의 `usage`에는 `input_tokens: 0`, `output_tokens: 0`이 `null`이나 생략이 아닌 숫자 `0`으로 기록된다.
  2. 종료 시점의 최종 사용량 이벤트와 완료 상태 변수에는 임시값 `0`이 최종 확정 합계(`input_tokens: 140`, `output_tokens: 35`)로 완전히 대체되어 기록된다.
- **보존 조건:** 초기 이벤트와 최종 이벤트 사이에 전달되는 텍스트·추론·도구 호출 델타의 순서와 내용은 사용량 상태 갱신으로 인해 누락되거나 변경되지 않아야 한다.
- **정상 대조와 적용 범위:** 단발(비스트리밍) 응답이 최종 확정 사용량을 한 번에 반환하는 경우를 정상 대조군으로 삼아, 스트리밍 경로의 최종 확정 사용량이 단발 응답의 확정치와 일치하는지 검증한다.
- **미정 규칙:** 해당 없음.

### EC-005. Anthropic 비캐시 입력 토큰 차감, 부분 미상 캐시 카운터 보존, OpenAI 총 입력 토큰 유지

- **설계 근거:** Anthropic 비캐시 입력 토큰은 알려진 캐시 읽기 및 쓰기를 제외하며, 부분적으로 미상인 캐시 카운터는 보존한다. OpenAI 전체 입력 토큰은 변경하지 않는다(`DO-03`).
- **필수 여부:** `required`
- **선행 조건:** 상위 공급자가 총 입력 토큰과 캐시 세부 카운터를 포함한 응답 사용량 데이터를 반환한다.
- **입력과 행동 순서:**
  1. 상위 공급자 사용량으로 `total_input: 1000`, `cache_read: 600`, `cache_write: 150`, `output: 80`이 주어진 상태에서 Anthropic 응답 변환 결과와 OpenAI 응답 변환 결과를 각각 확인한다.
  2. 상위 공급자 사용량으로 `total_input: 1000`, `cache_read: 400`만 알려지고 `cache_write`는 미상(생략 또는 미제공)인 데이터를 주입하여 Anthropic 응답과 OpenAI 응답의 사용량 필드를 확인한다.
  3. 상위 공급자 사용량으로 `total_input: 1000`이고 캐시 읽기·쓰기가 모두 미상인 데이터를 주입하여 두 프로토콜의 결과를 확인한다.
- **기대 결과:**
  1. 1단계에서 Anthropic 응답은 알려진 캐시 읽기(`600`)와 쓰기(`150`)를 차감한 비캐시 입력 토큰 `input_tokens: 250`과 함께 `cache_read_input_tokens: 600`, `cache_creation_input_tokens: 150`, `output_tokens: 80`을 반환하며, 동일 입력에 대해 OpenAI 응답은 전체 입력 토큰 `1000`을 차감 없이 그대로 유지한다.
  2. 2단계에서 Anthropic 응답은 알려진 `cache_read`(`400`)만 차감하여 `input_tokens: 600`과 `cache_read_input_tokens: 400`을 기록하고, 미상인 쓰기 카운터는 임의의 숫자로 꾸며내지 않은 채 부분 미상 상태를 보존한다. OpenAI 응답은 전체 입력 토큰 `1000`을 그대로 유지한다.
  3. 3단계에서 Anthropic 응답은 차감할 알려진 캐시 값이 없으므로 `input_tokens: 1000`을 유지하고 미상 캐시 카운터를 조작해 넣지 않는다.
- **보존 조건:** 출력 토큰(`output_tokens` / `completion_tokens`)과 응답 본문 콘텐츠는 입력 토큰 차감 연산 전후에 그대로 유지되어야 한다.
- **정상 대조와 적용 범위:** 캐시 적중이 없는 일반 응답(`total_input: 1000`)을 대조군으로 삼아, 캐시 읽기·쓰기가 모두 알려진 경우와 한쪽만 알려진 경우에서 Anthropic 차감 규칙과 OpenAI 총량 유지 규칙의 차이를 검증한다.
- **미정 규칙:** 해당 없음.

### EC-006. 알려진 캐시 읽기·쓰기 합계가 전체 입력 토큰을 초과하는 비정상 사용량 거부

- **설계 근거:** 알려진 캐시 합계가 전체 입력 토큰을 초과하는 경우(`cache sum exceeding total`)는 유효하지 않은 것으로 판정해야 한다(`DO-03`).
- **필수 여부:** `required`
- **선행 조건:** 단발 응답 및 스트리밍 완료 이벤트 변환기가 상위 공급자의 사용량 데이터를 검증하는 단계에 있다.
- **입력과 행동 순서:**
  1. 상위 사용량 데이터로 `total_input: 500`, `cache_read: 350`, `cache_write: 200`(합계 `550 > 500`)을 주입한다.
  2. 상위 사용량 데이터로 `total_input: 300`, `cache_read: 301`, `cache_write` 미상(단독 `301 > 300`)을 주입한다.
- **기대 결과:**
  1. 1단계와 2단계 모두 음수 `input_tokens`(`-50`, `-1`)를 반환하거나 조용히 `0`으로 깎아 정상 사용량인 것처럼 통과시키지 않고, 유효하지 않은 사용량 오류로 판정한다.
- **보존 조건:** 유효하지 않은 사용량이 감지되었을 때 잘못된 음수·위조 토큰 수치가 정상 확정 통계 변수에 기록되지 않아야 한다.
- **정상 대조와 적용 범위:** 알려진 캐시 합계가 전체 입력 토큰과 정확히 같은 경계(`total_input: 500, cache_read: 300, cache_write: 200` → 비캐시 `input_tokens: 0`으로 정상 유효)를 정상 대조군으로 삼아, 합계가 1이라도 초과하는 순간(`501 > 500`) 유효하지 않은 상태로 전환되는 경계를 검증한다.
- **미정 규칙:** 해당 없음.

### 묶음 3: 추론(Thinking) 표시 모드, 가짜 서명 금지, 히스토리 재전송 정제

사용량 계산과 더불어 응답의 내용 면에서 가장 민감한 경계는 모델의 추론(thinking) 출력과 그 이력의 다음 턴 재전송이다. 프록시는 추론이 활성화되었을 때 상위 요약을 표준 비서명 블록과 Codex 확장으로 전달해야 하지만, 추론이 생략·비활성화되었을 때는 상위가 비요청 추론 델타를 보내더라도 이를 차단해야 한다. 또한 이전 턴에서 생성된 추론·가림 블록이 다음 턴 요청의 대화 이력으로 돌아왔을 때는 형식만 검증한 뒤 상위 문맥에서 제거해야 한다.

### EC-007. 활성·적응형 추론의 기본 요약(`summarized`) 전환과 비서명 표준 블록 및 Codex 확장 동시 전달

- **설계 근거:** 활성(`enabled`) 및 적응형(`adaptive`) 추론은 기본적으로 요약(`summarized`) 모드로 동작하며, 요약 모드는 실제 상위 요약을 서명 없는 표준 `thinking` 콘텐츠·델타와 유지된 Codex 확장으로 전달하고 가짜 서명을 만들지 않는다(`DO-04`).
- **필수 여부:** `required`
- **선행 조건:** 요약 지원 백엔드 모델이 선택되어 있고, 상위 공급자가 추론 요약 텍스트(`"단계별 조건을 먼저 검토합니다."`)와 일반 응답 텍스트(`"최종 답변입니다."`)를 생성한다.
- **입력과 행동 순서:**
  1. `thinking: {"type": "enabled", "budget_tokens": 1024}`만 지정하고 `display` 필드를 생략한 요청을 단발 및 스트리밍으로 실행한다.
  2. `thinking: {"type": "adaptive"}`만 지정하고 `display` 필드를 생략한 요청을 단발 및 스트리밍으로 실행한다.
  3. 반환된 응답 콘텐츠 블록과 스트리밍 델타 이벤트, 그리고 Codex 확장 필드를 검사한다.
- **기대 결과:**
  1. 1단계와 2단계 모두 추론 표시 모드가 기본값인 `summarized`로 설정된다.
  2. 단발 응답과 스트리밍 델타 모두에서 상위 공급자의 실제 요약 텍스트(`"단계별 조건을 먼저 검토합니다."`)가 표준 `thinking` 블록 및 `thinking_delta`로 전달되며, 동시에 Codex 확장 데이터가 보존된다.
  3. 표준 `thinking` 블록과 스트리밍 이벤트 어디에도 임의로 생성된 `signature` 필드나 `signature_delta`가 포함되지 않는다.
- **보존 조건:** 추론 블록 뒤에 이어지는 일반 텍스트 블록(`"최종 답변입니다."`)과 도구 호출 블록의 내용·순서는 변형 없이 유지되어야 한다.
- **정상 대조와 적용 범위:** `display: "summarized"`를 명시적으로 지정한 요청을 정상 대조군으로 삼아, `enabled`와 `adaptive`에서 `display`를 생략했을 때의 출력 구조가 명시적 `summarized`와 일치하는지 검증한다.
- **미정 규칙:** 해당 없음.

### EC-008. 추론 생략·비활성(`omitted`/`disabled`) 시 비요청 상위 추론 델타 억제와 서명 조작 금지

- **설계 근거:** 생략(`omitted`) 또는 비활성(`disabled`) 추론은 비요청 상위 추론 델타를 포함해 모든 추론 출력을 억제하며, 가짜 서명을 생성하지 않는다(`DO-04`).
- **필수 여부:** `required`
- **선행 조건:** 상위 공급자가 요청 설정과 무관하게 비요청 추론 요약 델타(`"내부 추론 조각"`)와 일반 텍스트 델타(`"사용자에게 보일 응답"`)를 함께 방출하는 상황이다.
- **입력과 행동 순서:**
  1. `thinking` 파라미터를 아예 생략한 요청, `thinking: {"type": "disabled"}`인 요청, `thinking: {"type": "enabled", "budget_tokens": 1024, "display": "omitted"}`인 요청을 각각 전달한다.
  2. 상위 공급자 스트림에서 비요청 추론 델타 이벤트와 일반 텍스트 델타 이벤트를 연속으로 주입한다.
- **기대 결과:**
  1. 세 가지 요청 모두에서 상위 공급자가 보낸 추론 블록 및 추론 델타(`"내부 추론 조각"`)가 클라이언트 응답 및 스트림 이벤트에서 완전히 억제되어 방출되지 않는다.
  2. 가짜 `signature`, 빈 `thinking` 블록, 또는 임의로 꾸며낸 `redacted_thinking` 블록도 생성되지 않는다.
  3. 일반 텍스트 응답(`"사용자에게 보일 응답"`)과 완료 이벤트만 정상적으로 클라이언트에 전달된다.
- **보존 조건:** 추론 델타가 억제되는 동안에도 스트림의 메시지 식별자, 일반 텍스트·도구 호출 델타 순서, 최종 사용량 상태 변수는 정상 유지되어야 한다.
- **정상 대조와 적용 범위:** 동일 상위 스트림에 대해 `thinking: {"type": "enabled", "display": "summarized"}`에서는 추론 요약이 전달되는 것(`EC-007`)을 대조군으로 삼아, `thinking` 생략·`disabled`·`display: "omitted"` 세 경로에서 비요청 상위 추론 출력이 100% 차단되는지 검증한다.
- **미정 규칙:** 해당 없음.

### EC-009. 재전송된 유효 `thinking`·`redacted_thinking` 이력의 검증 후 상위 문맥 제외와 일반 텍스트·도구 호출 보존

- **설계 근거:** 재전송된 유효한 `thinking` 및 `redacted_thinking` 이력은 검증을 거친 뒤 백엔드 문맥에서 제외되며, 일반 텍스트와 도구 호출은 그대로 유지된다(`DO-04`).
- **필수 여부:** `required`
- **선행 조건:** 클라이언트가 다중 턴 대화를 이어가며 이전 어시스턴트 턴의 콘텐츠 배열에 `thinking`, `redacted_thinking`, `text`, `tool_use` 블록을 함께 담아 요청을 보낸다.
- **입력과 행동 순서:**
  1. 이전 어시스턴트 메시지에 유효한 `{"type": "thinking", "thinking": "이전 턴의 추론 요약"}`(서명 있음 및 서명 없음 모두 포함), 유효한 `{"type": "redacted_thinking", "data": "opaque_payload"}`, 일반 `{"type": "text", "text": "도구를 호출합니다."}`, `{"type": "tool_use", "id": "toolu_01", "name": "get_weather", "input": {"city": "Seoul"}}`가 순서대로 들어 있고, 이어서 사용자 메시지에 `tool_result`와 후속 질문이 담긴 요청을 `Messages`, `count`, `compact`에 전달한다.
  2. 검증 통과 후 상위 백엔드로 전달되는 문맥 메시지 배열 변수를 확인한다.
  3. 이전 어시스턴트 메시지에 필수 필드가 빠지거나 잘못된 자료형을 가진 `{"type": "thinking", "thinking": 12345}` 또는 `{"type": "redacted_thinking"}`(`data` 누락)가 포함된 요청을 전달한다.
- **기대 결과:**
  1. 1단계 요청은 서명 유무와 관계없이 유효한 재전송 추론·가림 이력으로 검증을 통과한다.
  2. 2단계의 상위 백엔드 문맥 변수에는 `thinking` 및 `redacted_thinking` 블록이 완전히 제외되어 전달되지 않으며, 함께 있던 일반 `text` 블록(`"도구를 호출합니다."`), `tool_use` 블록(`toolu_01`), 그리고 후속 `tool_result`와 사용자 질문은 원래 순서와 내용 그대로 유지된다.
  3. 3단계의 형식이 깨진 `thinking`·`redacted_thinking` 블록은 백엔드로 조용히 넘어가기 전에 입력 검증 오류로 거부된다.
- **보존 조건:** 추론 블록이 제거된 어시스턴트 메시지에서 남은 `text`와 `tool_use` 블록의 상대적 순서, 도구 호출 ID(`toolu_01`), 인자 객체(`{"city": "Seoul"}`)는 조금도 훼손되지 않아야 한다.
- **정상 대조와 적용 범위:** 처음부터 `text`와 `tool_use`만 포함된 다중 턴 이력을 정상 대조군으로 삼아, 유효한 `thinking`/`redacted_thinking` 블록이 추가되었을 때 검증 통과 후 만들어지는 상위 백엔드 문맥이 대조군과 동일해지는지 검증한다.
- **미정 규칙:** 해당 없음.

### 묶음 4: 추론 강도(Effort) 결정, 요약 제어 전달, 도구 지연 로딩(`eager_input_streaming`) 경계

추론 모드와 도구 정의가 백엔드 모델의 카탈로그 역량(capability)과 결합될 때, 프록시는 카탈로그가 지원하는 범위 안에서만 파생 설정을 선택하고 미지원 명시적 요구나 미지원 상위 제어는 단호히 거부하거나 생략해야 한다. 이 묶음은 카탈로그의 추론 강도(`effort`) 목록, 모델의 요약 지원 여부, 그리고 도구 정의의 `eager_input_streaming` 및 지연 로딩(`defer_loading`) 속성이 상위 요청과 검증 결과에 어떻게 반영되는지 검증한다.

### EC-010. 비활성 추론 파생 `effort`의 카탈로그 기반 선택(`none` 우선·최저 지원 단계 차선)과 명시적 미지원 `effort`의 무음 하향 금지

- **설계 근거:** 비활성 추론에서 파생된 `effort`는 카탈로그에서 `none`이 가능하면 `none`을 선호하고, 그렇지 않으면 지원되는 가장 낮은 카탈로그 `effort`를 선택한다. 반면 명시적으로 지정된 미지원 `effort`는 유효하지 않으며 조용히 하위 단계로 낮출 수 없다(`DO-05`).
- **필수 여부:** `required`
- **선행 조건:** 카탈로그에 두 모델이 등록되어 있다. 모델 A는 지원 `effort` 목록으로 `["none", "low", "medium", "high"]`를 가지고, 모델 B는 `"none"` 없이 `["low", "medium", "high"]`만 가진다.
- **입력과 행동 순서:**
  1. 모델 A를 대상으로 `thinking: {"type": "disabled"}`(명시적 `effort` 미지정) 요청을 보내고 상위 요청의 파생 `effort` 변수값을 확인한다.
  2. 모델 B를 대상으로 `thinking: {"type": "disabled"}`(명시적 `effort` 미지정) 요청을 보내고 상위 요청의 파생 `effort` 변수값을 확인한다.
  3. 모델 B(`"none"` 및 `"xhigh"` 미지원)를 대상으로 클라이언트가 명시적 `effort`를 `"none"` 또는 `"xhigh"`로 지정한 요청을 전달한다.
- **기대 결과:**
  1. 1단계에서 모델 A에 대한 상위 요청의 파생 `effort`는 `"none"`으로 결정된다.
  2. 2단계에서 모델 B에 대한 상위 요청의 파생 `effort`는 모델 B의 최저 지원 단계인 `"low"`로 결정된다.
  3. 3단계에서 모델 B가 지원하지 않는 명시적 `effort`(`"none"` 또는 `"xhigh"`)를 지정한 요청은 `"low"`나 `"high"`로 조용히 하향·대체되지 않고 즉시 유효성 오류로 거부된다.
- **보존 조건:** 3단계에서 미지원 명시적 `effort`가 거부될 때 상위 공급자 호출은 발생하지 않으며, 카탈로그의 모델별 지원 `effort` 배열 상태는 변하지 않는다.
- **정상 대조와 적용 범위:** 모델 B에 명시적으로 지원 단계인 `"low"` 또는 `"medium"`을 지정한 정상 요청을 대조군으로 삼아, 비활성 추론에 의한 자동 파생(`"low"` 선택 허용)과 명시적 미지원 지정(거부 필수)의 처리 차이를 검증한다.
- **미정 규칙:** 해당 없음.

### EC-011. 요약 지원 모델의 명시적 `display` 상위 반영과 요약 미지원 모델의 가짜 요약 제어 생성 금지

- **설계 근거:** 요약 지원 모델(`summary-capable models`)에서는 명시적 `display`가 상위 요약 요청에 영향을 미치며, 요약 미지원 모델에서는 지원되지 않는 요약 제어(`unsupported summary knob`)를 조작해 넣지 않아야 한다(`DO-05`).
- **필수 여부:** `required`
- **선행 조건:** 카탈로그에 추론 요약을 지원하는 모델 S(`supports_reasoning_summary: true`)와 추론 요약을 지원하지 않는 모델 N(`supports_reasoning_summary: false`)이 준비되어 있다.
- **입력과 행동 순서:**
  1. 요약 지원 모델 S에 대해 `thinking: {"type": "enabled", "budget_tokens": 1024, "display": "summarized"}` 요청과 `thinking: {"type": "enabled", "budget_tokens": 1024, "display": "omitted"}` 요청을 각각 전달하고 생성된 상위 공급자 요청의 요약 제어 필드를 비교한다.
  2. 요약 미지원 모델 N에 대해 추론 요청을 전달하고 생성된 상위 공급자 요청 객체에 요약 제어 필드가 포함되었는지 확인한다.
- **기대 결과:**
  1. 1단계에서 모델 S의 상위 공급자 요청은 클라이언트의 명시적 `display` 값(`"summarized"` 대 `"omitted"`)에 맞추어 상위 요약 요청 설정이 서로 다르게 반영된다.
  2. 2단계에서 모델 N의 상위 공급자 요청에는 모델 N이 지원하지 않는 상위 요약 제어 필드가 임의로 조작·삽입되지 않는다.
- **보존 조건:** 요약 제어 필드의 포함·생략 여부와 무관하게, 요청의 `messages`, 모델 식별자, 파생 `effort` 등 나머지 상위 요청 필드는 정상 유지되어야 한다.
- **정상 대조와 적용 범위:** 요약 지원 모델 S와 요약 미지원 모델 N을 나란히 대조하여, 상위 요약 요청 파라미터가 오직 카탈로그상 요약 지원 능력이 있는 모델에서만 생성·조절되는지 검증한다.
- **미정 규칙:** 해당 없음.

### EC-012. 도구 `eager_input_streaming` 불리언 자문 속성 수용과 지연 로딩(`defer_loading`) `false` 허용·`true` 거부

- **설계 근거:** 도구의 `eager_input_streaming`은 불리언 자문 속성으로 수용하며, 지연 로딩이 `false`인 경우는 무해하게 허용하되 `true`인 지연 수명주기 및 조작된 호스팅 도구 수명주기는 지원하지 않는다. 유효한 도구와 실제 프로토콜·도구 안전성은 보존해야 한다(`DO-06`, `DO-08`).
- **필수 여부:** `required`
- **선행 조건:** 클라이언트가 하나 이상의 사용자 정의 도구(`custom tool`)를 포함한 요청을 `Messages`, `count`, `compact` 경로에 전달한다.
- **입력과 행동 순서:**
  1. 유효한 도구 정의에 `eager_input_streaming: true`, 두 번째 도구에 `eager_input_streaming: false`, 세 번째 도구에 `defer_loading: false`를 함께 포함한 요청을 전달한다.
  2. 도구 정의에 `eager_input_streaming: "yes"`(비불리언)를 포함한 요청을 전달한다.
  3. 도구 정의에 `defer_loading: true`를 포함한 요청과, 백엔드가 지원하지 않는 호스팅 도구 수명주기(가짜 서버 실행 결과나 조작된 호스팅 도구 상태)를 요구하는 요청을 각각 전달한다.
- **기대 결과:**
  1. 1단계 요청은 세 엔드포인트 모두에서 유효한 요청으로 수락되며, 세 도구의 `name`, `description`, `input_schema`가 상위 공급자 도구 목록에 온전히 보존되어 전달된다.
  2. 2단계의 비불리언 `eager_input_streaming` 요청은 스키마 검증 오류로 거부된다.
  3. 3단계의 `defer_loading: true` 요청과 미지원 호스팅 도구 수명주기 요청은 조용히 무시되거나 가짜 실행 결과로 꾸며지지 않고 명시적 오류로 거부된다.
- **보존 조건:** 1단계에서 자문 속성(`eager_input_streaming`, `defer_loading: false`)을 처리할 때 도구의 필수 스키마 제약과 프로토콜 안전성 검증이 우회되거나 약화되지 않아야 한다.
- **정상 대조와 적용 범위:** 부가 속성이 없는 기본 도구 정의(`name`, `description`, `input_schema`)를 정상 대조군으로 삼아, `eager_input_streaming: true/false` 및 `defer_loading: false`의 무해 통과와 `eager_input_streaming` 타입 오류·`defer_loading: true` 거부를 대조한다.
- **미정 규칙:** 해당 없음.

### 묶음 5: 모델 퍼사드 해석, 카탈로그 장애 처리, 실시간 미디어 경계 및 오류·비밀값 전달

요청 제어와 도구 검증을 마친 뒤 실제 백엔드 모델을 결정하고 외부 세션을 연결하거나 오류를 회신할 때, 프록시는 카탈로그 상태와 프로토콜 소유권을 정직하게 반영해야 한다. 이 묶음은 공인 `claude-*` 퍼사드 모델의 해석 순서, 비퍼사드 미등록 모델과 빈 카탈로그의 실패 처리, 실시간(`Realtime`) 미디어의 클라이언트 소유 경계, 그리고 실패 발생 시 원문 오류 보존과 비밀값 마스킹을 검증한다.

### EC-013. 공인 `claude-*` 퍼사드의 설정 모델·최신 카탈로그 기본값 순차 해석과 정적 모델 임의 생성 금지

- **설계 근거:** 공인된 `claude-*` 퍼사드 모델은 설정된 백엔드 모델이 있으면 이를 사용하고, 없으면 정적 모델을 임의로 만들지 않고 최신 카탈로그 기본값을 사용한다(`DO-07`).
- **필수 여부:** `required`
- **선행 조건:** 모델 해석 단위에 백엔드 모델 설정 변수와 동적 모델 카탈로그 상태가 주입될 수 있다.
- **입력과 행동 순서:**
  1. 백엔드 모델 설정이 `"codex-configured-model"`로 지정되어 있고 카탈로그 기본값이 `"catalog-default-v2"`인 상태에서, 공인된 퍼사드 모델명(예: `"claude-sonnet-4-20250514"` 등 공인 `claude-*` 식별자)으로 요청을 전달한다.
  2. 백엔드 모델 설정을 비운(미설정) 상태에서, 카탈로그 기본값이 `"catalog-default-v2"`일 때 동일한 공인 `claude-*` 퍼사드 모델명으로 요청을 전달한다.
  3. 이후 최신 카탈로그가 갱신되어 카탈로그 기본값이 `"catalog-default-v3"`으로 바뀐 상태에서 다시 동일한 공인 `claude-*` 퍼사드 모델명으로 요청을 전달한다.
- **기대 결과:**
  1. 1단계에서는 설정된 백엔드 모델이 우선하여 상위 요청 모델이 `"codex-configured-model"`로 해석된다.
  2. 2단계에서는 하드코딩된 정적 모델명이 아니라 현재 카탈로그의 기본값인 `"catalog-default-v2"`로 해석된다.
  3. 3단계에서는 갱신된 최신 카탈로그 기본값인 `"catalog-default-v3"`으로 즉시 해석되며, 코드에 고정된 구형 정적 모델명을 만들어내지 않는다.
- **보존 조건:** 퍼사드 모델명이 백엔드 모델명으로 해석되는 과정에서 요청의 나머지 파라미터와 클라이언트 측에 필요한 응답 형식 문맥은 보존되어야 한다.
- **정상 대조와 적용 범위:** 카탈로그에 직접 등록된 백엔드 모델명을 그대로 요청한 경우를 대조군으로 삼아, 공인 `claude-*` 퍼사드 요청이 설정 유무와 카탈로그 갱신 전후에 따라 정확한 대상 모델로 연결되는지 검증한다.
- **미정 규칙:** 해당 없음.

### EC-014. 미등록 비퍼사드 모델 거부 및 빈 카탈로그·카탈로그 조회 불가 시 명시적 오류 반환

- **설계 근거:** 알 수 없는 비퍼사드 모델은 유효하지 않으며, 카탈로그가 비어 있거나 사용할 수 없는 상태는 명시적 오류로 유지되어야 한다(`DO-07`).
- **필수 여부:** `required`
- **선행 조건:** 모델 해석 단위에 카탈로그 상태(정상 목록, 빈 목록, 조회 실패 상태)를 주입할 수 있다.
- **입력과 행동 순서:**
  1. 정상 카탈로그(`["catalog-default-v2", "codex-mini"]`)가 로드된 상태에서, 공인 `claude-*` 퍼사드도 아니고 카탈로그에도 없는 미등록 모델명(`"unknown-custom-model-99"`)으로 요청을 전달한다.
  2. 백엔드 모델 오버라이드가 설정되지 않은 상태에서 카탈로그가 비어 있거나(`[]`) 카탈로그 조회가 실패(unavailable)한 상태를 만들고, 공인 `claude-*` 퍼사드 모델 및 일반 모델로 각각 요청을 전달한다.
- **기대 결과:**
  1. 1단계의 미등록 비퍼사드 모델 요청은 카탈로그 기본값으로 조용히 대체되지 않고 유효하지 않은 모델 오류로 거부된다.
  2. 2단계의 빈 카탈로그 또는 카탈로그 불능 상태에서는 임의의 정적 모델명을 꾸며내어 요청을 진행하지 않고, 카탈로그 비가용·비어 있음을 나타내는 명시적 오류를 반환한다.
- **보존 조건:** 모델 해석 실패 시 상위 공급자 생성 호출이나 과금·세션 변수가 오염되지 않아야 하며, 이후 카탈로그가 정상 복구되면 다음 요청은 다시 정상 처리되어야 한다.
- **정상 대조와 적용 범위:** 정상 카탈로그에서 등록된 모델(`"codex-mini"`)과 공인 퍼사드(`EC-013`)가 성공하는 것과 대조하여, 미등록 비퍼사드 모델과 빈·불능 카탈로그 상태에서 무음 폴백이 전혀 일어나지 않는지 검증한다.
- **미정 규칙:** 해당 없음.

### EC-015. 실시간(`Realtime`) 호스트 미디어 비소유·사이드밴드 중계 경계와 상위 오류 원문 보존 및 실제 비밀값 마스킹

- **설계 근거:** 실시간 미디어는 클라이언트가 소유하며 프록시는 호출 생성과 사이드밴드 중계만 수행하고, Python·Rust의 HTTP 전용 범위는 변경하지 않는다. 오류 출력에 실제 자격증명을 노출하거나 실제 오류를 은폐하지 않는다(`DO-08`, `SKILL.md` 오류 전달 검증).
- **필수 여부:** `required`
- **선행 조건:** 실시간 호출 생성·사이드밴드 중계 단위와 HTTP/사이드밴드 오류 변환 단위가 테스트 입력을 받을 수 있다.
- **입력과 행동 순서:**
  1. 실시간 세션 생성 단위에 SDP offer와 합성된 상위 SDP answer를 주고 반환된 answer·call ID를 비교한다. 사이드밴드 중계 단위에는 메모리 안의 프레임 입력을 주고 출력 프레임·호출 인자를 비교한다. 장치 소유 여부나 Python·Rust의 API 부재는 소스존재·프로세스·장치 상태 테스트로 검증하지 않으며, 이 사례의 자동화 assertion에서 제외한다.
  2. 상위 공급자 또는 실시간 사이드밴드가 실패 응답(예: 상태 코드 `429` 또는 `502`, `error.code: "rate_limit_exceeded"`, `error.message: "Quota exceeded for bearer sk-live-SECRET123456789 with key Bearer tok_ABCDEF98765"`)을 반환하는 상황을 주입한다.
- **기대 결과:**
  1. 1단계에서 프록시는 호출 생성 응답과 사이드밴드 제어·이벤트 중계 데이터만 반환·전달하며, 미디어 스트림 자체는 클라이언트 소유로 남긴다. Python·Rust 범위에는 실시간 미디어 소유 기능이 추가되지 않고 HTTP 전용 범위가 유지된다.
  2. 2단계에서 실패는 빈 응답, 가짜 성공 응답, 또는 무음 타임아웃으로 바뀌지 않으며, 원래의 상태(`429`/`502`), `error.code`(`"rate_limit_exceeded"`), 그리고 진단 문구(`"Quota exceeded for ..."`)가 보존되어 반환된다.
  3. 동시에 오류 메시지 내부의 실제 비밀값(`sk-live-SECRET123456789`, `tok_ABCDEF98765`)만 마스킹 처리되고, 오류 원인 파악에 필요한 나머지 진단 문구는 통째로 삭제되거나 일반 문구로 덮어써지지 않으며, 사용자의 전체 입력 프롬프트 덤프가 오류에 덧붙여지지 않는다.
- **보존 조건:** 오류 마스킹 후에도 오류 객체의 상태 코드, 오류 타입·코드 식별자, 비밀값이 아닌 일반 진단 텍스트는 그대로 유지되어야 한다.
- **정상 대조와 적용 범위:** 비밀값이 포함되지 않은 일반 상위 오류(`"Invalid parameter: temperature"`)가 원문 그대로 전달되는 경우를 대조군으로 삼아, 비밀값이 포함된 오류에서 오직 비밀 토큰 값만 가려지고 진단 정보와 실패 상태는 보존되는지 검증한다.
- **미정 규칙:** 해당 없음.

### EC-016. 전체 입력 토큰 누락·음수 하위 카운터 등 미명시 복합 사용량 이상치 및 미명시 구버전 세부 규칙의 판정 보류

- **설계 근거:** 브리프에 명시되지 않은 제품 전반의 구버전 동작이나 세부 규칙은 추측하지 않고 `design_pending` 또는 1차 범위 외로 정당화해야 한다(`proxy083-design-only-brief.md` 16행).
- **필수 여부:** `design_pending`
- **선행 조건:** 상위 공급자가 비표준적이거나 불완전한 메타데이터·사용량 조합을 반환하거나, 브리프에 언급되지 않은 구버전 확장 필드가 포함된 요청이 유입된다.
- **입력과 행동 순서:**
  1. 상위 사용량 데이터에서 전체 입력 토큰(`total_input`) 자체가 누락된 채 부분 캐시 읽기 카운터만 도착하거나, 개별 캐시 하위 카운터에 음수(`cache_read: -5`)가 들어온 경우를 주입한다.
  2. 브리프의 7개 승인 항목에 명시되지 않은 구버전 비표준 헤더나 레거시 전용 확장 필드를 포함한 요청을 전달한다.
- **기대 결과:** 설계 브리프가 확정한 의무(`DO-01`~`DO-08`)를 침해하지 않는 선에서 동작해야 하나, 해당 세부 입력에 대해 거부할지 무시할지 또는 어떤 세부 오류 코드를 부여할지는 현재 설계 문서만으로 단일 정답을 확정할 수 없으므로 임의의 단정적 테스트 오라클을 강제하지 않는다.
- **보존 조건:** 미정 영역과 무관한 확정 의무(`EC-001`~`EC-015`)의 판정 기준과 기존 유효 전송·계정 격리는 어떤 경우에도 약화되지 않아야 한다.
- **정상 대조와 적용 범위:** `total_input`이 존재하고 알려진 캐시 합계가 총량을 초과하는 명확한 무효 사례(`EC-006`) 및 부분 미상 카운터 정상 보존 사례(`EC-005`)와 구별하여, 설계 문서가 규칙을 지정하지 않은 경계를 표시한다.
- **미정 규칙:** (1) 상위 공급자가 `total_input`을 생략하고 캐시 하위 카운터만 보낼 때 이를 오류로 거부할지 `0`으로 둘지 여부, (2) 브리프에 언급되지 않은 레거시 전용 비표준 필드의 구체적 오류 코드·메시지 규격이 미정이다. 사용자 또는 추가 설계 결정이 있기 전까지 임의 정책을 필수 요구로 만들지 않는다.

## 최종 범위와 남은 사항

- 사례 총수와 상태별 수: 총 16개 설계 사례(`required` 15개: `EC-001`~`EC-015`, `design_pending` 1개: `EC-016`) 및 별도 분리된 사용자 실사용 검증 항목 3개(`UV-001`~`UV-003`, `blocked: user_validation_required`). 현재 1차 설계 작성 단계 완료 기준 `pending` 15개, `blocked`(`design_pending`) 1개이다.
- 발견한 구현 결함과 보완 증거: 1차 격리 작성 단계이므로 제품 소스 코드와 테스트를 읽지 않았으며, 구현 결함 확인 및 보완은 2차 단계에서 수행한다.
- 설계의 미정·모순과 영향: 브리프에 명시된 0.8.3 핵심 의무(`DO-01`~`DO-08`) 간에는 상호 모순이 없다. 다만 전체 입력 토큰이 누락된 상태에서의 부분 캐시 이상치 처리와 브리프에 언급되지 않은 구버전 비표준 필드의 세부 처리는 브리프 범위 밖이므로 `EC-016`(`design_pending`)으로 분리하여 2차·3차에서 임의 규칙을 강제하지 않도록 경계를 설정하였다.
- 미실행 테스트·독립 검토와 이유: 1차 설계 전용(DESIGN ONLY) 작성 지침에 따라 코드·테스트 열람 및 터미널 실행을 수행하지 않았다. `EC-001`~`EC-015`의 표준 유닛테스트 대응·실행(2차)과 항목별 순차 독립 검토(3차)가 남아 있다.
- 선언한 범위의 검증 완료 여부: 1차 설계 기반 엣지 케이스 도출 완료(전체 레드팀 절차 기준으로는 2차·3차 및 사용자 실사용 검증 대기 상태인 부분 진행 단계).
- 제품 전체 목표와 남은 완료 기준: 2차에서 프로젝트 표준 테스트 러너로 `EC-001`~`EC-015`의 입출력·변수 검증을 연결·보완하고, 3차에서 단일 active 항목 순차 독립 검토를 수행한다. `UV-001`~`UV-003`은 사용자 수행 대기로 별도 남기며, 이를 새 릴리스 승인 게이트로 추가하지 않는다. 사용자 요청에 따른 릴리스 완료는 공식 테스트 정리·구현 검증·공개 배포 확인으로 판단하고, 실사용 미확인은 별도로 보고한다.
